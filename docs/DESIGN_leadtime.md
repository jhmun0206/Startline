# Startline — 착수일 역산

**설계 의도, 변화 과정, 현재 상태, 계획 — 외부 검토 반영판**

- 작성일: 2026-09-22 · **개정: 2026-10-07 (v2: Perplexity·Gemini 검토와 bdc9328 결과 반영)**
- 단계: Phase 1 · 실사용 검증 중
- 스택: macOS / SwiftUI + EventKit

> 마감이 아니라 **착수**를 관리한다.
> 다만 앱이 내놓는 착수일은 정답이 아니라 **가정에 기반한 대략적 권장일**이다.
> Phase 1에서 확인할 것은 계산의 정확도가 아니다. **불완전한 추정이어도 착수 판단에 도움이 되는지**다.

---

## 1. 설계 의도

기존 캘린더는 **마감 N분 전**에 알린다. 그런데 3시간짜리 온라인 강의를 마감 1시간 전에 알려주면 이미 늦었다. 실제로 중요한 시점은 마감이 아니라 **늦지 않게 시작할 수 있는 마지막 시점**이다.

```
착수 권장일 = 마감 − (작업량 ÷ 일일 투입량) − 대기 기간
```

v1의 `착수일 = 마감시각 − 필요 소요시간`은 작업량과 달력 시간을 같은 것으로 취급했다. v2에서는 아래 네 값을 분리한다(→ 4장 중기).

| 값 | 뜻 | 예 |
|---|---|---|
| **작업량** | 실제로 손을 써야 하는 총 시간 | 12시간 |
| **일일 투입량** | 이 일에 하루 쓸 수 있는 시간 (가정) | 하루 3시간 |
| **대기 기간** | 내가 일하지 않아도 흘러야 하는 시간 | 서류 발급 3일, 배송, 회신 대기 |
| **착수 권장일** | 위 셋으로 낸 결과. 날짜 단위 | 마감 4일 전 |

### 놓치는 일정 네 종류

| 유형 | 내용 | 예 |
|---|---|---|
| **A** | 심리적 회피 대상 | 하기 싫은 행정 처리. 중요도가 아니라 회피도에 비례해 미룬다 |
| **B** | 소요시간이 알림 리드타임보다 긴 작업 | 3시간짜리 강의, 마감 일요일 23:59 |
| **C** | 준비 기간이 필요한 목표 | 자격증 시험. 지금 시작해야 하는지를 모른다 |
| **D** | 일정에 딸린 준비 작업 | 미팅보다 그 전에 해야 할 일들이 진짜 관리 대상 |

유형 C가 핵심이다. 남은 기간과 필요 기간을 비교해야 알 수 있는데 사람은 그 계산을 하지 않는다. 유형 A는 계산으로 풀리지 않는다. 첫 행동을 작게 만드는 쪽(4장 측정·문구 실험)에서 다룬다.

### 경쟁 비교 (v2 수정)

v1에서는 "소요시간을 알림 트리거 계산에 쓰는 앱은 없다, 그래서 해자다"라고 썼다. **틀렸다.** Motion은 소요시간·마감·가용 시간을 받아 작업 블록을 캘린더에 자동 배치하고, 긴 작업은 쪼개서 넣는다. 역산 자체는 이미 있다. Todoist도 2025년 1월부터 작업 날짜와 별도로 **deadline**을 두고, 소요시간(duration) 필드도 있다.

| | 마감 관리 | 소요시간 입력 | 시작 시점 산출 | 일정–할일 연결 | 방식 |
|---|---|---|---|---|---|
| Apple / Google 캘린더 | O | X | X | X | — |
| Todoist / TickTick | O (날짜 + deadline 분리) | O | X (사용자가 날짜를 정함) | 일부 | 수동 |
| Motion | O | O | **O** | O | 하루 전체를 자동 배치 |
| **Startline** | O | O | O | O | 착수 시점만 알림 |

차별점은 "계산을 한다"가 아니라 **무게**에 있다.

> **하루 전체를 자동으로 계획하지 않고, 마감에 늦지 않도록 지금 시작해야 하는 일을 가볍게 알려준다.**

Motion은 사용자의 하루를 넘겨받고, Startline은 착수 신호만 준다. 이 차이가 실제로 의미 있는지는 아직 검증 전이다. "해자"라는 표현은 철회한다.

## 2. 변화 과정

Phase 1에서 공식 그대로 구현했다. 소요시간을 입력받아 마감에서 빼고, 결과를 분 단위까지 화면과 알림에 표시했다. 실사용에서 **세 겹의 문제**가 차례로 드러났다.

### 입력 — 사용자가 소요시간을 모른다

"투자자산운용사 시험이 며칠 걸리는지"를 알았다면 애초에 늦지 않았다. 모르는 것을 물으면 빈칸으로 남고, 빈칸이면 핵심 기능이 죽는다. 기획 단계에서 최상위 리스크로 예측했고 실사용으로 확인됐다.

### 계산 — 달력 시간으로 빼면 사람의 하루를 무시한다

사람은 자는 시간, 근무 시간, 기존 일정을 고려해 시작 시점을 잡는다. 앱은 그냥 뺀다. 작업량과 달력 시간을 구분하지 않은 게 원인이다.

### 표시 — 없는 정밀도를 꾸며낸다

12시간짜리 작업의 착수 시각을 분 단위로 말하는 것 자체가 거짓이다. 사람은 12시간을 연속으로 하지 않는다.

### 실제로 나온 값

```
마감   9월 26일 (토) 16:00
소요   12시간
─────────────────────────────
16:00 − 12h = 같은 날 04:00   → "9월 26일 (토) 새벽 4시에 시작"
```

자고 있는 시각이다. 그리고 그 12시간 안에 자는 시간이 들어 있다. 실제로는 전날이나 그 이전에 시작해야 맞다. **시각만 틀린 게 아니라 날짜가 틀렸다.**

> 정정: 이 사례를 처음 설명할 때 "오늘 04:00"으로 잘못 계산했다. 같은 날 04:00이 맞다. 이 착오 때문에 아래 ③이 이 사례를 고칠 거라고 잘못 판단했다.

### 검토 후 기각한 안들

**① 소요시간을 아예 묻지 않는다 — "며칠 전"만 받는다**

다른 투두 앱이 안 묻는 건 착수 시점을 계산하지 않아서 필요가 없기 때문이다. 따라 하면 "며칠 전부터 할까"라는 판단이 다시 사용자에게 돌아가는데, 그 판단을 대신하는 게 유형 C의 해법이었다. 단, "N일 전" 경로는 소요시간을 모를 때의 대안으로 유지한다(현재 칩 UI).

**② 활동 시간대를 설정받아 그 안에서만 역산한다**

새벽 4시는 안 나오지만 "12시간을 연속으로 한다"는 가정은 남는다. 그럴듯해 보일 뿐 틀린 값이고 설정만 는다. v2의 「일일 투입량」은 이 안과 다르다. 시간대가 아니라 **하루에 쓸 양**을 가정하고, 그 가정을 숨기지 않는다.

**③ 계산은 그대로 두고 표시만 날짜 단위로 내린다 — 구현됨(bdc9328), 문제는 미해결**

규칙: 착수가 마감과 **같은 날이면 시각까지, 다른 날이면 날짜만**. 문구는 `StartMomentText` 한 곳으로 모았다(「9월 7일 (월)에 시작」, 「오늘」/「내일」). 알림도 다른 날이면 착수일 아침 9시에 울린다.

하지만 위 사례는 같은 날 04:00이라 **"새벽 4시"가 그대로 나온다.** 표시로는 계산 오류를 덮을 수 없다는 게 확인됐다. 계산 재설계는 **BL-058**로 열려 있다.

**④ 하루 가용 시간 8시간을 앱이 일괄 기본값으로 정한다 — v1 계획, 철회**

8시간은 누구에게도 맞지 않는 값이고, 숨겨진 기본값은 결과를 신뢰할 근거를 없앤다. → 기본값은 두되 **결과 옆에 가정을 노출**한다(4장).

**⑤ 알림 3단계 중 「위험(착수 +1시간)」 — 철회**

착수 후 1시간이 지났다고 위험한 게 아니다. 위험은 **남은 시간이 작업량보다 적어질 때** 생긴다. BL-031의 개념이 틀렸다.

## 3. 현재 상태 (bdc9328 기준, 테스트 320개 통과)

| 항목 | 상태 | 비고 |
|---|---|---|
| 착수 시점 역산 엔진 | 동작 | 소요시간 / N일 전 두 경로. **작업량과 달력 시간 미구분** |
| 일정에 딸린 할 일 (유형 D) | 동작 | 부모 일정 기준 상대 저장. 일정이 옮겨지면 같이 따라감 |
| 착수 시점 문구 | 통일됨 | `StartMomentText` 단일 출처. 같은 날 → 시각, 다른 날 → 날짜 |
| 알림 시각 | 부분 완화 | 다른 날 → 착수일 09:00 / 같은 날 → 계산 시각 그대로 |
| 알림 판정 로직 | **불일치** | `NotificationScheduler`는 아직 옛 판정 사용 (BL-055) |
| 알림 단계 | 3단계 | 예고 −1일 / 착수 / 위험 +1시간. 위험 단계는 철회 예정 |
| 알림 개수 한도 | **미검증** | 64개 한도는 iOS에서 Apple이 확인. macOS는 확인 안 됨. 현재 60개로 롤링 |
| 같은 날 새벽 착수 | **미해결** | 위 사례. BL-058 |
| 불가능한 계획 | **미처리** | 이미 시간이 부족해도 아무 말 없음 |
| 소요시간 입력 마찰 | 미해결 | 칩 UI로 완화. 모를 때 대안은 "N일 전" |
| 실제 착수 여부 | **측정 안 함** | 알림 받고 시작했는지 기록이 없다 |

기능은 다 돌아가는데, 값이 사람의 하루와 안 맞고 **그 값이 도움이 되는지 알 방법도 없다.**

## 4. 계획 (v2)

순서를 바꾼다. 계산을 더 다듬기 전에 **측정부터** 한다. 단기 수정은 명백한 오류만 막는다.

### 지금 — 2주 측정

**착수의 정의:** 알림을 받았다는 것도, 앱을 열었다는 것도 아니다. **첫 구체 행동을 했는가**로 본다. 예: 교재를 펴고 첫 문제를 풀었다.

기록할 것(항목당):

| 항목 | 값 |
|---|---|
| 권장 착수일 vs 실제 착수일 | 날짜 2개 |
| 권장 시점 이후 착수까지 걸린 시간 | 일 단위 |
| 시작 안 한 이유 | 시간 없음 / 추정 불신 / 첫 행동 불명확 / 회피 / 이미 시작함 |
| 추정치를 고쳤는가 | 예·아니오, 고친 값 |
| 마감을 지켰는가 | 예·아니오 |

**첫 행동 문구 실험:** 같은 기간에 일부 알림 문구를 "투자자산운용사 공부 시작" 대신 **"오늘 첫 문제 5개를 풀어보세요"** 같은 첫 행동으로 바꿔본다. 유형 A(회피)에 계산보다 이쪽이 더 듣는지 본다.

**기록 방식 (2026-10-07 결정):** 개발용 임시 로그가 아니라 **제품 데이터**로 설계한다. 배포 후 「사용자 자신의 데이터로 보여주는 기능」(원칙 2)과 Phase 2 AI 참고값의 근거가 된다. 기기 안에만 저장하고 외부로 전송하지 않으며, 지금은 화면에 노출하지 않는다. 앱이 자동으로 잡을 수 있는 값만 기록하고, 「시작 안 한 이유」는 측정 기간 동안 수기로 메모한다.

판단 기준: 2주 뒤 "시작 안 한 이유"의 분포가 다음 작업을 정한다. "추정 불신"이 많으면 계산(중기)이 먼저고, "첫 행동 불명확"·"회피"가 많으면 문구와 입력이 먼저다.

### 단기 — 명백한 오류만 막는다

1. **알림이 마감을 넘지 않게.** "9시 이전이면 9시로 당긴다"를 일괄 적용하면, 마감 08:00·착수 05:00 같은 경우 알림이 마감 뒤로 밀린다. 조정된 알림 시각은 **어떤 경우에도 마감보다 앞서야** 한다. 넘으면 조정하지 않는다. (현재 구현은 다른 날일 때만 9시로 옮기므로 이 버그는 없다. 같은 날로 확장할 때 지켜야 할 조건이다.)
2. **새 날 새벽 착수.** 같은 날 새벽으로 계산된 착수는 늦추면 시간이 준다. 늦출 게 아니라 **전날로 당기는 쪽**이 맞을 가능성이 높다. 방식은 BL-058에서 정한다.
3. **불가능한 계획을 알린다.** 지금부터 해도 작업량이 남은 시간보다 크면 착수일을 과거로 보여주지 않고 **"현재 설정으로는 마감까지 시간이 부족해요"**라고 말한다.

### 중기 — 가정이 보이는 계산

- 네 값(작업량 / 일일 투입량 / 대기 기간 / 착수 권장일)을 분리해 계산한다. 입력한 값은 그대로 저장하고 계산만 바뀐다(원칙 1).
- 결과 옆에 가정을 붙인다: **「하루 3시간 기준 · 변경」**. 그리고 **"다른 할 일과 겹치는 건 반영하지 않아요"**를 명시한다.
- 이건 원칙 4("계산 방식을 고르게 하지 않는다")와 충돌하지 않는다. 방식이 아니라 **가정 하나**를 보여주고 고칠 수 있게 하는 것이다. 다만 「일일 투입량」·「대기 기간」이라는 말은 화면에 쓰지 않는다.
- 대기 기간은 입력을 하나 더 늘리므로 기본은 0, 필요한 항목만 연다.

### 중기 — 알림 묶음 (단계는 유지)

하루 한 번 묶음으로 바꾸되, **묶음 안에서 단계를 유지**한다.

```
오늘 아침 알림
  오늘 시작할 일        2개
  내일 시작할 일 (예고)  1개
  시작 시점 지났는데 아직  1개
```

- 「위험 +1시간」 단계는 없앤다. 대신 "시작 시점이 지났는데 아직"을 묶음 안에 둔다. 진짜 위험(남은 시간 < 작업량)은 단기 3번의 "시간이 부족해요"가 맡는다.
- **재계산 한계:** 반복 트리거는 예약할 때의 내용을 그대로 보낸다. 앱을 안 열면 묶음 내용이 바뀌지 않는다. 선택지:
  - A. 고정 문구 반복("오늘 시작할 일을 확인하세요") + 내용은 앱에서
  - B. 며칠치 요약을 미리 예약해두고 앱을 열 때마다 갈아끼움 (현재 롤링 스케줄러의 연장)
  - C. 백그라운드 갱신 (macOS에서 신뢰도 확인 필요)
  - 현재 판단은 **B**. 측정 후 확정.
- **macOS 알림 한도를 실측한다.** 64개는 iOS 기준이다.
- 미완료 이월 피로는 열린 문제다. 3개월 미룬 항목이 매일 끼면 알림 자체를 무시하게 된다. 이월 상한이나 묶어서 접기 등은 측정 결과를 보고 정한다.

### Phase 2 — AI는 참고값을 낸다

사용자는 목표만 넣고 AI가 작업량을 **제안**한다. 단정하지 않는다(원칙 3).

```
"9월 28일 투자자산운용사 시험"

  개념 훑기   약 3일
  문제 풀이   약 4일
  모의고사    약 2일
  오답 정리   약 2일
  ──────────────────
  예상 필요   약 11일 (하루 3시간 기준)
  남은 기간     8일

  지금 설정으로는 시간이 부족해요
```

> **Phase 1의 목표 (v2 수정):** v1에서는 "AI가 들어올 자리를 만드는 것"이라고 썼다. 바꾼다. Phase 1의 목표는 **불완전한 추정이어도 착수 판단에 도움이 되는지 확인하는 것**이다. 도움이 안 된다면 AI로 추정을 정교하게 해도 소용없다.

## 5. 의견을 구했던 것 — 검토 후 결론

### Q1. 소요시간을 묻는 것이 맞나?

**결론: 묻는다. 다만 「소요시간」 하나가 아니라 작업량으로 묻고, 모르면 "N일 전"으로 빠질 수 있게 한다.** 빈칸 구간은 칩 UI와 "N일 전" 경로로 버틴다. 묻는 게 실제로 도움이 되는지는 측정 항목 "추정 불신"·"추정 수정"으로 확인한다.

### Q2. 하루 가용 시간을 앱이 정하나, 사용자가 정하나?

**결론: 둘 다 아니다. 앱이 기본값을 두되, 결과 옆에 가정으로 보여주고 그 자리에서 고칠 수 있게 한다.** 숨겨진 8시간은 철회. 설정 화면이나 온보딩 질문은 만들지 않는다.

### Q3. 착수 시점을 날짜로만 말해도 충분한가?

**결론: 충분하지 않다.** v1의 "날짜는 덜 정확하지만 틀리지는 않다"는 틀렸다. 날짜도 틀릴 수 있다(위 사례). 날짜/시각 단위 규칙은 bdc9328로 들어갔고 그대로 두되, 그것만으로는 계산 오류가 안 고쳐진다. 결과는 **가정에 기반한 대략적 권장일**로 말한다.

### Q4. 알림을 아침 묶음 하나로 줄이면 놓침이 늘까?

**결론: 묶되 단계를 지우지 않는다.** 예고와 "지났는데 아직"을 묶음 안에 남긴다. 「위험 +1시간」은 개념이 틀려 없앤다. 반복 트리거의 재계산 한계와 macOS 한도는 확인할 것.

### 근본 질문 — 아직 답 없음

> **"알림을 받고 실제로 시작한 적이 있는가."**

계산이 완벽해도 알림을 받고 안 움직이면 실패고, 계산이 좀 틀려도 움직였으면 성공이다. 4장의 2주 측정이 이 질문에 답하기 위한 것이다.
