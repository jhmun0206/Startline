# Startline 백로그

미뤄둔 작업을 모아두는 단일 창구. 기획 명세서(`Startline_명세서_v0.2.md`)의 Phase 구분을 따른다.

## 운영 규칙

1. 작업 중 **나중에 하기로 미룬 것**이 생기면 즉시 이 파일에 추가한다. 별도 요청 없이 매번 자동으로 한다.
2. 추가 대상:
   - 사용자가 "나중에", "일단 넘어가자"라고 한 것
   - 구현 중 임시방편으로 처리한 것 (TODO, 하드코딩, 예외 미처리)
   - 알려진 버그나 미완성 동작
   - 성능·구조상 나중에 리팩터링이 필요한 것
3. 완료한 항목은 **삭제하지 않는다.** 완료 표시 + 커밋 해시를 남기고 「완료」 절로 옮긴다.
4. 매 작업 종료 보고 때, 이번에 추가된 항목이 있으면 알린다.

### BL-001 · 그리드 칸에서 긴 제목이 잘려 구분 불가

- **우선순위:** P2 (호버 미리보기로 완화했으나 **2026-09-08 그 미리보기를 껐다** — BL-044)
- **Phase:** 1 (월간 그리드)
- **배경:** 그리드 칸 폭이 좁아 제목 앞부분만 보인다. F1 일정이 전부 `FOR...`로만 표시돼 Practice / Qualifying / Race를 구분할 수 없다. 같은 접두사를 공유하는 일정군에서 일반적으로 발생하는 문제라, 칸 폭을 넓히는 것으로는 해결되지 않는다.
- **발생 위치:** [MonthGridView.swift](../Startline/MonthGridView.swift) — `EventBar`
- **해결 방향:** 세 갈래를 검토한다. (a) 같은 날 일정들의 공통 접두사를 감지해 생략하고 변별력 있는 뒷부분을 남기는 축약 로직, (b) 앞부분 대신 뒷부분을 남기는 `truncationMode(.head)` 적용, (c) 칸 밀도를 낮추고 제목 2줄 표시.
- **2026-09-05 갱신 — 상당 부분 완화됨:** 그리드 일정 바에 **호버 미리보기**를 붙였다(명세서 6.3). 마우스를 올리면 잘리지 않은 전체 제목과 시간·장소·캘린더가 팝오버로 나온다. F1 일정을 구분하지 못하던 문제는 이걸로 해결된다.
  **다만 항목은 닫지 않는다.** 미리보기는 한 번에 하나씩만 보여주므로, 그리드를 **한눈에 훑어 여러 일정을 구분하는** 원래 문제는 남아 있다. 우선순위는 P1 → **P2**로 낮춘다.
- **등록일:** 2026-09-05

### BL-002 · 월 이동 스냅 스크롤 미구현 (1차 시도 실패, 되돌림)

- **우선순위:** P2
- **Phase:** 1
- **배경:** 현재 이전/다음 버튼만 있다. 명세서 부록 C 원문 — "이전달/다음달 클릭버튼 혹은 상하 스크롤로. 대신 스크롤로 하면 페이지의 9/10 정도가 해당 월로 채워지면 자동으로 슬그머니 맞춰지면서 해당 월만 보여지게 해줘."
- **발생 위치:** [MonthGridView.swift](../Startline/MonthGridView.swift) — `MonthGridView.grid`

#### 1차 시도 실패 기록 (2026-09-05 구현 `284ce2d` → 2026-09-06 되돌림)

`ScrollView` + `LazyVStack` + 커스텀 `ScrollTargetBehavior` 로 만들었으나 **그리드가 통째로 비어 보이고, 머리글은 2026년 9월인데 우측 패널은 2024년 9월을 가리키는** 상태가 되어 되돌렸다.

**원인 1 — 앵커에 픽셀 오프셋이 아니라 배열 인덱스를 넣었다 (연도 어긋남의 직접 원인)**

```swift
anchor.settledY = CGFloat(index)   // 24 를 "24pt" 로 저장
```

`updateTarget` 은 이 값을 픽셀 오프셋으로 읽는다.

```
startPage = (24 / 700).rounded() = 0    → months[0]
```

`months` 는 현재 달 기준 앞뒤 24개월이므로 `months[0]` 은 **정확히 24개월 전**이다.
2026년 9월에서 24개월 전 = **2024년 9월.** 보고된 연도와 정확히 일치한다.
올바른 값은 `CGFloat(index) * 페이지높이` 였다. 그런데 페이지 높이는 `GeometryReader` 가 잡히기 전이라 `buildMonths()` 시점에 알 수 없다 — **초기화 시점 자체가 잘못된 설계였다.**

**원인 2 — 그리드가 빈 이유 (부분 확인)**

잘못된 앵커로 계산된 오프셋과 `.scrollPosition(id:)` 가 서로 다른 위치를 가리키면서, `LazyVStack` 이 실제로 만들어 둔 페이지 밖으로 스크롤 위치가 밀려났다. 화면에 그릴 페이지가 없으니 아무것도 안 나온다.
여기에 `MonthPage` 높이를 `GeometryReader` 의 `proxy.size.height` 로 잡았는데, 첫 레이아웃에서 이 값이 확정되기 전에 페이지가 만들어지면 높이 0 으로 배치될 수 있다. **이쪽은 코드로 확인했을 뿐 실행 중 관측은 못 했다.**

**원인 3 — 머리글과 선택 날짜가 따로 논 이유 (설계 결함)**

되돌리기 전에는 **기준이 둘**이었다.

| | 무엇을 보고 그렸나 |
|---|---|
| 머리글 | `manager.displayedMonth` |
| 그리드 내용 | 스크롤이 보여주는 페이지 |
| 우측 패널 | `manager.selectedDate` |

스크롤 위치 → `onChange` → `setDisplayedMonth` → **그 안에서 `selectedDate` 까지 바꾼다.**
즉 스크롤이 선택 날짜를 건드리는 구조였고, 스크롤 위치가 어긋나는 순간 셋이 전부 따로 놀았다.
되돌린 지금은 `displayedMonth` 하나만 보고 그린다. 머리글·그리드·선택 날짜가 어긋날 수 없다. (20개 시나리오 검증 통과)

#### 다음에 시도할 때 주의할 점

1. **macOS 14 에는 스크롤 오프셋을 읽는 API 가 없다.** `onScrollGeometryChange` 는 macOS 15+ 다. 그래서 `ScrollTargetBehavior`(값 타입, 호출 사이 상태 없음)에 "직전에 어디 있었나"를 알려주려면 바깥 참조 타입에 기록하는 수밖에 없는데, **그 값을 언제 무엇으로 초기화할지가 이번 실패의 핵심이었다.** 페이지 높이를 모르는 시점에 초기화하면 안 된다.
2. **기준을 하나로 유지할 것.** 스크롤 위치가 `selectedDate` 를 바꾸게 두면 안 된다. 스크롤은 `displayedMonth` 만 옮기고, `selectedDate` 는 사용자가 날짜를 눌렀을 때만 바뀌어야 한다. `setDisplayedMonth` 가 선택 날짜를 손보는 현재 동작도 스크롤과 함께 쓰면 위험하다.
3. **페이지 높이는 `GeometryReader` 로 확정된 뒤에만 쓴다.** 초기 스크롤 위치 지정도 높이가 잡힌 다음이어야 한다.
4. 트랙패드 두 손가락 스크롤은 `DragGesture` 로 잡히지 않는다(스크롤 휠 이벤트). 직접 오프셋을 다루는 방식은 쓸 수 없고 `ScrollView` 를 거쳐야 한다.
5. 임계값(6/7)의 산술은 12건 검증을 통과했었다. **계산식이 아니라 초기화와 상태 관리가 문제였다.** 다시 만들 때 계산식은 재사용해도 된다.
6. 되돌리면서 **월별 캐시(`dayEvents(forMonth:)`)는 남겼다.** 스크롤과 무관하게 유용하고, 다시 시도할 때 그대로 쓸 수 있다. (BL-008 참고)

- **등록일:** 2026-09-05
- **1차 시도 실패 기록:** 2026-09-06

- **등록일:** 2026-09-05
- **2026-09-13 완료.** `ericmun.Startline` → `com.ericmun.Startline`

  어디에도 번들 ID 문자열이 없었다. (Info.plist 는 `GENERATE_INFOPLIST_FILE` 로 생성된다)

### BL-005 · 중복 일정 판정 기준 (결정 기록 — 변경 금지)

- **우선순위:** P3
- **Phase:** 1
- **배경:** 여러 캘린더에 중복 등록된 일정(공휴일, 생일)을 그리드에서 한 건으로 묶는 기준은 **같은 날 안에서 `종일여부 + 시작시각 + 제목` 완전 일치**다. **이는 의도된 동작이며 임의로 완화하지 않는다.** 기준을 느슨하게 하면 서로 다른 일정을 같은 것으로 잘못 묶는 오탐이 생기고, 이는 일정이 화면에서 사라지는 형태로 나타나 미탐보다 훨씬 위험하다.
- **발생 위치:** [CalendarManager.swift](../Startline/CalendarManager.swift) — `DayEvent.groupingKey(for:)`
- **해결 방향:** 지금은 손대지 않는다. 실사용 중 오탐·미탐 사례가 실제로 누적되면 그때 재검토한다. 알려진 미탐 유형: 캘린더 제공자마다 공휴일 이름이 다른 경우("추석" vs "추석 연휴").
- **등록일:** 2026-09-05

- **2026-09-08 덧붙임 — 판정에 캘린더를 반영했다.**
  「같은 이름·시각의 서로 다른 일정이 하나로 묶이고 삭제가 일부만 되는」 사고가 났다. (BL-048)
  묶기가 캘린더를 전혀 보지 않아, 사용자가 같은 캘린더에 만든 별개의 일정까지 합쳐졌다.

  규칙을 **「한 묶음에 한 캘린더는 최대 하나만 기여한다」** 로 바꿨다.
  이는 판정을 **완화가 아니라 강화**하는 것이므로 BL-005 의 결정과 같은 방향이다.
  「추석」과 「추석 연휴」가 다른 일정이라는 판단은 그대로 유지된다.

  ※ 「묶기 판정에 캘린더 식별자를 키로 포함」하는 방식은 채택하지 않았다.
  그렇게 하면 *같은 캘린더끼리만* 묶이고 *다른 캘린더는 안 묶여* 결과가 정반대가 된다.


### BL-007 · 권한 거부 상태에서 시스템 설정 변경을 감지하지 못함

- **우선순위:** P2
- **Phase:** 1

- **해결 방향:** 앱이 다시 활성화될 때(`NSApplication.didBecomeActiveNotification`) `refreshAccessState()`를 호출하고, 승인으로 바뀌었으면 이어서 로드한다. 그러면 안내 문구에서 재실행 요구를 뺄 수 있다.
- **등록일:** 2026-09-05

### BL-008 · 일정 조회가 메인 스레드에서 동기 실행됨

- **우선순위:** P3
- **Phase:** 2
- **배경:** `eventStore.events(matching:)`를 메인 스레드에서 직접 호출한다. 한 달 범위·소수 캘린더에서는 체감되지 않아 그대로 뒀다. 캘린더 수가 많거나 스냅 스크롤(BL-002)로 조회 범위가 넓어지면 스크롤이 끊길 수 있다.

### BL-040 · 되돌리기(undo) 미지원

### BL-042 · 「그만두기」가 할 일 변경까지 취소하지는 않는다

- **우선순위:** P2
- **Phase:** 1
- **배경:** 「일정 수정」 시트에서 딸린 할 일 줄을 눌러 할 일 폼으로 들어간 뒤 **「저장」을 누르면 그 시점에 커밋된다.** 이후 일정 시트를 「그만두기」로 닫아도 그 할 일 변경은 되돌아가지 않는다. 취소되는 것은 **일정 본문의 미저장 변경뿐**이다.

  일정은 EventKit, 할 일은 SwiftData에 저장되어 **두 저장소를 하나의 트랜잭션으로 묶을 수 없다.** 할 일 폼의 「저장」은 그 자체로 완결된 동작이라 되돌릴 지점이 없다.

  **사용자는 「그만두기」를 눌렀으니 "전부 취소했다"고 오해할 수 있다.** 시트 하나 안에서 벌어진 일인데 일부만 남는다.
- **재현 조건:** 일정 수정 시트 → 딸린 할 일 줄 클릭 → 소요시간 변경 → 「저장」 → 「← 일정으로」 → 시트를 「그만두기」로 닫기. 할 일의 소요시간은 바뀐 채로 남아 있다.
- **발생 위치:** [EventEditorView.swift](../Startline/EventEditorView.swift) — `editingLinkedTask` 전환 / [TaskEditorView.swift](../Startline/TaskEditorView.swift) — `save()` 의 `saver.commit`
- **해결 방향:** **BL-040(되돌리기)이 붙으면 함께 풀린다.** 시트를 여는 시점에 undo 그룹을 열고, 「그만두기」에서 그 그룹을 통째로 되돌리면 저장소가 달라도 한 덩어리로 취소된다.

  그 전까지의 완화책은 두 갈래다. (a) 할 일 폼의 「저장」을 「확인」으로 바꾸고 일정 시트의 저장 시점에 함께 반영한다 — 일정 본문과 기준이 같아지지만, 저장하지 않고 닫으면 할 일 변경도 날아가므로 그 사실을 알려야 한다. (b) 문구를 바꿔 「그만두기」가 일정 변경만 취소한다는 것을 드러낸다. 완화책을 먼저 넣을지는 실사용에서 실제로 헷갈리는지 보고 정한다.
- **관련:** BL-040
- **등록일:** 2026-09-08

### BL-056 · 「일정만 보기」·「할 일만 보기」가 찾기 어렵다

- **우선순위:** P3
- **Phase:** 1
- **기능은 이미 다 있다. 새로 만들 것이 없다.** 둘 다 필터 팝오버(헤더의 깔때기 아이콘 →
  「보여줄 것」)에 있다.

  | 하려는 것 | 지금 방법 |
  |---|---|
  | 할 일만 보기 | 팝오버의 **「전체 해제」** — 캘린더만 꺼진다. 클릭 한 번 |
  | 캘린더만 보기 | 팝오버의 **「할 일」 체크 해제** |

  **한쪽을 끄면 상대가 그 몫을 가져간다.** 빈 자리로 남지 않는다.
  [GridLayout.swift](../Startline/GridLayout.swift) `WeekLayout.build` 에 그 결정이 적혀 있다 —
  「할 일이 있으면 그 몫을 남긴다. 할 일이 없으면 일정이 칸을 다 쓴다.」

  실제로 돌려 확인했다 (같은 날 일정 8개 + 할 일 3개, 칸 높이 110pt):

      할 일 끔          일정 막대 2 → 4개
      캘린더 전체 해제   할 일 막대 2 → 3개

  `showsTasks` = 할 일 막대 전체 / `showsTaskSpan` = 마감까지의 점선 구간만.
  일정만 끄는 **단일 토글은 없다.** 「전체 해제」가 같은 결과를 낸다.

- **그래서 남은 문제는 「없는 기능」이 아니라 「찾기 어려움」이다.**
  팝오버를 열어야만 보이고, 「보여줄 것」이라는 이름이 「일정만/할 일만 보기」로 읽히지 않는다.
- **검토했다 버린 안:** 헤더에 캘린더/할 일 체크박스를 새로 단다
  → **헤더 컨트롤이 6개에서 8개가 된다.** 오른쪽 정렬로 겨우 정리한 줄이라 기각. (`7925c26`)
- **보류 이유:** 입력 방식·표시 단위·반복 등 **구조 결정이 진행 중**이라 그리드에 무엇이
  얼마나 그려지는지가 바뀔 수 있다. 지금 발견성을 손보면 구조가 바뀔 때 또 손대게 된다.
  **구조 확정 후 재판단한다.** (명세서 부록 B)
- **발생 위치:** [MonthGridView.swift](../Startline/MonthGridView.swift) — `CalendarFilterList`
- **관련:** `7925c26`(헤더 정렬), BL-002
- **등록일:** 2026-09-22

- **선행:** BL-069 (일정 반복 입력)
- **설계 근거:** [docs/DESIGN_direction.md](DESIGN_direction.md) 3장 결정 2
- **관련:** BL-019, BL-069
- **등록일:** 2026-10-07

- **설계 (2026-10-08 결정) — 기록만. 구현은 나중.**

  **기본 구조:** 회차마다 실제 할 일 레코드를 만든다. 틀(템플릿) 레코드는 화면에 보이지 않는다.

  **체크리스트 — 구현 시 9개 모두 적용·테스트. 하나도 빼지 말 것.**

  - [ ] **1. 재생성 금지.** 사용자가 지운 회차는 「생성 제외」로 기록하고, 다시 채울 때 만들지 않는다.
        완료한 회차도 다시 만들지 않는다. 완료 레코드를 나중에 정리하더라도 **회차 처리 기록은 지우지 않는다.**
  - [ ] **2. 중복 생성 금지.** 생성 키는 **「틀 ID + 회차 키」**. 한 일정에 준비가 여러 개 붙어도 구분된다.
        같은 키는 몇 번 요청돼도 하나만 생성한다(멱등). 여러 재채움 경로가 동시에 돌아도 마찬가지다.
  - [ ] **3. 개별 수정 보호.** 틀을 「이후 모두」로 고치면 아직 안 지난 미완료 복사본에 적용한다.
        단 **제목·마감·알림을 개별 수정한 복사본은 제외**한다.
  - [ ] **4. 생성 범위 = 가까운 범위 ∪ 화면 범위.**
        · 가까운 범위: 준비 알림 시각(알림 없음이면 준비 마감)이 지금부터 30일 안인 회차
        · 화면 범위: 현재 그리드 표시 범위(앞뒤 달 일부 포함)와 준비 막대(알림~마감)가 겹치는 회차.
          부모 일정이 화면 밖이어도 준비 막대가 화면에 걸리면 포함한다
        · 멀리 넘겨봤을 때 그 사이를 전부 채우지 않는다. 표시 범위에 필요한 회차만
  - [ ] **5. 알림 없음.** 생성 기준은 준비 마감이다. 화면 표시를 숨긴다는 뜻이 아니다.
  - [ ] **6. 앱 안에서 삭제.**
        · 한 회차: 그 회차의 미완료 준비 삭제
        · 이후 모두: 그 이후 미완료 준비 삭제
        · 완료한 준비는 남긴다
        · 확인창 문구에 한 줄: 「미완료 준비도 함께 지워지고, 이후 준비는 만들지 않아요. 완료한 건 남아요.」
  - [ ] **7. 「이후 모두」 삭제는 틀 삭제가 아니다.** 틀에 종료 경계를 기록한다. 과거 복사본의 출처를 보존한다.
  - [ ] **8. 일정 반복 입력(BL-069).** 「안 함 / 매일 / 매주 / 매월」 칩 한 줄 + 아래에 「다음 일정: 3월 31일」
        미리보기 한 줄. **31일 매월 반복은 지원 OS 에서 실제 EventKit 생성 결과를 테스트한다.**
  - [ ] **9. 알림 재채움 (BL-033 갱신).** 실행 중 날짜 변경(`NSCalendarDayChanged`)·잠자기 해제(`didWake`)·
        일정 변경·주기 실행 시 재조정한다. 창을 닫아도 앱 실행은 유지한다. 로그인 자동 실행은 선택
        (`SMAppService`, 샌드박스 서명 빌드에서 등록·해제·재로그인 검증). 문서·문구에는 「보장」이 아니라
        **「앱이 실행 중이면 계속 갱신, 종료 중에는 이미 예약된 알림만 유지」**로 표현한다.
        `NSBackgroundActivityScheduler` 를 정확한 타이머로 가정하지 말 것.

  **회차를 못 찾았을 때 — 자동 삭제 판별은 이번 범위가 아니다.**
  「그 회차가 없다」는 이유만으로 준비를 지우지 않는다. 날짜가 옮겨진 회차를 삭제로 오인할 수 있다.
  - 회차를 못 찾으면 연결과 준비 데이터를 유지한다
  - 해당 준비의 알림은 **보류**하고 「연결된 일정을 확인할 수 없어요」를 표시한다
  - 다시 찾으면 날짜를 따라 옮기고 알림을 재예약한다
  - 독립 할 일 전환은 사용자가 직접 할 때만
  - 외부 삭제 자동 판별은 별도 항목(BL-071)

  **추가**

### BL-031 · (폐기) 「위험」 단계 시점이 잠정값 (착수마감 + 1시간)
- **폐기:** 2026-10-07 방향 전환 — [docs/DESIGN_direction.md](DESIGN_direction.md). 이미 철회. 남아 있던 코드(`riskDelay`·위험 단계)는 알림 1단계화(BL-067)에서 걷어낸다.

- **2026-10-07 철회 — 개념 오류. 위험은 남은 시간 < 작업량일 때다.**
  착수 후 1시간이 지났다고 위험한 것이 아니다. 「+1시간을 몇으로 할까」는 틀린 질문이었다.
  진짜 위험(지금부터 해도 시간이 모자람)은 BL-061 이 맡는다.
  **코드는 아직 그대로다** — `riskDelay` 와 위험 단계는 BL-059(알림 묶음)에서 함께 걷어낸다.
  설계 근거: [docs/DESIGN_leadtime.md](DESIGN_leadtime.md) 2장 ⑤

- **우선순위:** P3
- **Phase:** 1
- **배경:** 명세서 9.1 은 위험 단계 시점을 "착수마감 경과"라고만 적었다. 구체적인 값이 없어 **+1시간**으로 잡았다. 너무 짧으면 시작하자마자 경고가 오고, 너무 길면 이미 손쓸 수 없을 때 온다.
- **발생 위치:** [NotificationScheduler.swift](../Startline/NotificationScheduler.swift) — `riskDelay`
- **해결 방향:** 2주 실사용에서 이 알림이 유용했는지 관찰해 정한다. 작업 길이에 비례시키는 방법(예: 소요시간의 20%)도 후보다. 리드타임이 하루 단위인 항목에 1시간은 너무 촘촘할 수 있다.
- **등록일:** 2026-09-06

### BL-055 · (흡수) 알림 스케줄러가 통합 판정을 쓰지 않는다
- **흡수:** 2026-10-07 방향 전환 — [docs/DESIGN_direction.md](DESIGN_direction.md). 알림을 1단계로 바꾸는 작업(BL-067)에 흡수된다. 옛 판정 자체가 사라진다.

- **우선순위:** P3
- **Phase:** 1
- **배경:** 「위험」·「놓침」 판정을 `ResolvedTask` 한 곳으로 모았고(BL-051) 배너·「할 일」 섹션·
  「기한 지난 할 일」이 모두 그것을 부른다. **알림 스케줄러만 옛 조건을 그대로 쓴다.**

      NotificationScheduler.swift:228   guard task.status == .notStarted else { continue }

  실무상 지금 문제는 없다. `guard fireDate > now` 가드가 있어 이미 지난 시각은 예약되지 않고,
  3단계는 착수마감에서 고정 오프셋으로 계산되므로 결과가 어긋나지 않는다.
  다만 **판정이 두 벌로 남아 있다는 사실**은 그대로다.
- **왜 남겨 두나:** 알림 3단계는 「시작 전날 / 시작 시각 / 시작 + riskDelay」라 `isAtRisk` 의
  불리언 판정과 성질이 다르다. 억지로 끼워 맞추면 오히려 읽기 어려워진다.
  묶을지, 묶는다면 어떤 모양으로 할지 따로 설계가 필요하다.
- **관련:** BL-051, BL-010(알림 3단계)
- **등록일:** 2026-09-14
