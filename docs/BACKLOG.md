# Startline 백로그

미뤄둔 작업을 모아두는 단일 창구. 기획 명세서(`Startline_명세서_v0.2.md`)의 Phase 구분을 따른다.

## 운영 규칙

1. 작업 중 **나중에 하기로 미룬 것**이 생기면 즉시 이 파일에 추가한다. 별도 요청 없이 매번 자동으로 한다.
2. 추가 대상:
   - 사용자가 "나중에", "일단 넘어가자"라고 한 것
   - 구현 중 임시방편으로 처리한 것 (TODO, 하드코딩, 예외 미처리)
   - 알려진 버그나 미완성 동작
   - 성능·구조상 나중에 리팩터링이 필요한 것
3. 완료한 항목은 **삭제하지 않는다.** 완료 표시 + 커밋 해시를 남기고 「완료」 절로 옮긴다.
4. 매 작업 종료 보고 때, 이번에 추가된 항목이 있으면 알린다.

## 열린 항목

### BL-001 · 그리드 칸에서 긴 제목이 잘려 구분 불가

- **우선순위:** P1
- **Phase:** 1 (월간 그리드)
- **배경:** 그리드 칸 폭이 좁아 제목 앞부분만 보인다. F1 일정이 전부 `FOR...`로만 표시돼 Practice / Qualifying / Race를 구분할 수 없다. 같은 접두사를 공유하는 일정군에서 일반적으로 발생하는 문제라, 칸 폭을 넓히는 것으로는 해결되지 않는다.
- **발생 위치:** [MonthGridView.swift](../Startline/MonthGridView.swift) — `EventBar`
- **해결 방향:** 세 갈래를 검토한다. (a) 같은 날 일정들의 공통 접두사를 감지해 생략하고 변별력 있는 뒷부분을 남기는 축약 로직, (b) 앞부분 대신 뒷부분을 남기는 `truncationMode(.head)` 적용, (c) 칸 밀도를 낮추고 제목 2줄 표시. 현재 툴팁(`.help`)은 마우스를 올려야만 보이므로 대책이 되지 못한다.
- **등록일:** 2026-09-05

### BL-002 · 월 이동 스냅 스크롤 미구현

- **우선순위:** P2
- **Phase:** 1 (월간 그리드)
- **배경:** 현재 이전/다음 버튼만 있다. 레이아웃을 먼저 세우기 위해 스크롤 방식을 다음 단계로 미뤘다.
- **명세서 근거:** 4.2 및 부록 B 원문 — "상하 스크롤로. 대신 스크롤로 하면 페이지의 9/10 정도가 해당 월로 채워지면 자동으로 슬그머니 맞춰지면서 해당 월만 보여지게 해줘."
- **발생 위치:** [MonthGridView.swift](../Startline/MonthGridView.swift) — `MonthGridView.grid`
- **해결 방향:** `ScrollView` + `.scrollTargetBehavior(.paging)`을 먼저 시도한다. 9/10 임계값은 기본 페이징 동작과 다르므로 `ScrollTargetBehavior` 프로토콜을 직접 구현해야 할 가능성이 높다. 스크롤 전환 시 앞뒤 달 일정을 미리 읽어둬야 하므로 `CalendarManager.loadEvents(from:to:)` 호출 범위 재설계가 함께 필요하다.
- **등록일:** 2026-09-05

### BL-003 · 위젯 익스텐션 추가 시 배포 타겟 재확인

- **우선순위:** P2
- **Phase:** 2 (WidgetKit)
- **배경:** 프로젝트·타겟 레벨 `MACOSX_DEPLOYMENT_TARGET`은 현재 모두 14.6이다. 다만 새 타겟을 추가하면 Xcode가 현재 SDK 기준 기본값(26.x)을 넣을 수 있어, 위젯 타겟 생성 직후 확인이 필요하다.
- **발생 위치:** `Startline.xcodeproj/project.pbxproj` — 신규 익스텐션 타겟의 빌드 설정
- **해결 방향:** 위젯 타겟 생성 직후 Build Settings에서 배포 타겟을 확인하고, 앱 타겟과 어긋나면 맞춘다. 명세서 3장 기준은 macOS 14.0+.
- **등록일:** 2026-09-05

### BL-004 · Bundle Identifier가 역방향 도메인 관례에 어긋남

- **우선순위:** P1
- **Phase:** 3 (배포)
- **배경:** 현재 `ericmun.Startline`. 관례상 `com.ericmun.Startline` 형태가 맞다. App Group은 이미 `group.com.ericmun.startline`로 잡혀 있어 표기가 서로 어긋나 있다.
- **발생 위치:** `Startline.xcodeproj/project.pbxproj` — `PRODUCT_BUNDLE_IDENTIFIER`
- **해결 방향:** App Store Connect에 앱을 등록하기 **전에** 바꾼다. 등록 후에는 변경이 불가능하다. 변경 시 함께 손봐야 하는 것: 프로비저닝 프로파일, App Group 컨테이너 경로, 이미 승인된 캘린더 접근 권한(번들 ID가 바뀌면 TCC가 새 앱으로 인식해 재승인 필요). SwiftData 스토어를 붙이기 전에 처리하는 편이 마이그레이션 부담이 적다.
- **등록일:** 2026-09-05

### BL-005 · 중복 일정 판정 기준 (결정 기록 — 변경 금지)

- **우선순위:** P3
- **Phase:** 1
- **배경:** 여러 캘린더에 중복 등록된 일정(공휴일, 생일)을 그리드에서 한 건으로 묶는 기준은 **같은 날 안에서 `종일여부 + 시작시각 + 제목` 완전 일치**다. **이는 의도된 동작이며 임의로 완화하지 않는다.** 기준을 느슨하게 하면 서로 다른 일정을 같은 것으로 잘못 묶는 오탐이 생기고, 이는 일정이 화면에서 사라지는 형태로 나타나 미탐보다 훨씬 위험하다.
- **발생 위치:** [CalendarManager.swift](../Startline/CalendarManager.swift) — `DayEvent.groupingKey(for:)`
- **해결 방향:** 지금은 손대지 않는다. 실사용 중 오탐·미탐 사례가 실제로 누적되면 그때 재검토한다. 알려진 미탐 유형: 캘린더 제공자마다 공휴일 이름이 다른 경우("추석" vs "추석 연휴").
- **등록일:** 2026-09-05

### BL-006 · 외부 캘린더 변경이 앱에 자동 반영되지 않음

- **우선순위:** P2
- **Phase:** 1
- **배경:** `EKEventStoreChanged` 알림을 구독하지 않는다. 앱이 열려 있는 동안 캘린더 앱이나 구글에서 일정을 고치면, 새로고침 버튼을 누르거나 달을 옮기기 전까지 화면이 낡은 상태로 남는다. EventKit 연동을 최소 범위로 먼저 세우느라 미뤘다.
- **발생 위치:** [CalendarManager.swift](../Startline/CalendarManager.swift) — `loadEvents(from:to:)` 호출 시점
- **해결 방향:** `NotificationCenter`에서 `.EKEventStoreChanged`를 구독해 현재 표시 범위를 다시 읽는다. 알림이 연달아 오므로 디바운스가 필요하다. 명세서 8장의 동기화 레이어를 설계할 때 함께 정리한다.
- **등록일:** 2026-09-05

### BL-007 · 권한 거부 상태에서 시스템 설정 변경을 감지하지 못함

- **우선순위:** P2
- **Phase:** 1
- **배경:** 권한 거부 화면이 "허용한 뒤 앱을 다시 실행해 주세요"라고 안내한다. 실제로 재실행 없이는 복구되지 않는다. 권한 상태를 앱 시작 시 한 번만 읽기 때문이다.
- **발생 위치:** [ContentView.swift](../Startline/ContentView.swift) — `AccessDeniedView` / [CalendarManager.swift](../Startline/CalendarManager.swift) — `refreshAccessState()`
- **해결 방향:** 앱이 다시 활성화될 때(`NSApplication.didBecomeActiveNotification`) `refreshAccessState()`를 호출하고, 승인으로 바뀌었으면 이어서 로드한다. 그러면 안내 문구에서 재실행 요구를 뺄 수 있다.
- **등록일:** 2026-09-05

### BL-008 · 일정 조회가 메인 스레드에서 동기 실행됨

- **우선순위:** P3
- **Phase:** 2
- **배경:** `eventStore.events(matching:)`를 메인 스레드에서 직접 호출한다. 한 달 범위·소수 캘린더에서는 체감되지 않아 그대로 뒀다. 캘린더 수가 많거나 스냅 스크롤(BL-002)로 조회 범위가 넓어지면 스크롤이 끊길 수 있다.
- **발생 위치:** [CalendarManager.swift](../Startline/CalendarManager.swift) — `loadEvents(from:to:)`
- **해결 방향:** 조회와 일자별 분류를 백그라운드로 옮기고 결과만 메인에서 반영한다. `EKEvent`는 스레드 간 전달이 안전하지 않으므로, 백그라운드에서는 화면 표시에 필요한 값만 담은 별도 모델로 변환해 넘겨야 한다. BL-002와 함께 다루는 편이 낫다.
- **등록일:** 2026-09-05

### BL-009 · 칸이 너무 낮으면 "+N" 표시가 칸 밖으로 넘침

- **우선순위:** P3
- **Phase:** 1
- **배경:** 창을 크게 줄여 한 칸에 바가 하나도 못 들어가면, 표시 가능 개수가 0이 되어 `+N`만 남는데 그 `+N`을 그릴 높이조차 없어 칸 경계를 넘어 그려진다.
- **재현 조건:** 앱 창 높이를 최소(560pt)까지 줄이고, 6주짜리 달에서 일정이 있는 날을 본다.
- **발생 위치:** [MonthGridView.swift](../Startline/MonthGridView.swift) — `DayCell.capacity(forHeight:)`
- **해결 방향:** 표시 가능 개수가 0이면 `+N` 대신 작은 점 하나로 대체하거나, 창 최소 높이를 올려 칸 높이를 보장한다. 후자가 간단하지만 좁은 화면을 포기하는 선택이므로 실사용 후 판단한다.
- **등록일:** 2026-09-05
